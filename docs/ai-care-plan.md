# AI 辅助关怀文案 —— 实施计划

状态：本文件写成时的架构判断（第 3 节"必须先有后端代理"）已经被一个更简单的方案绕开——
详见文末"更新：BYOK 架构已上线"。原有的三阶段功能规划（自由文本理解/多因素合成/长期叙事总结）
仍然有效，尚未按 Phase 1/2/3 完整实现，只先做了最基础的自由对话。

关联背景：《「心情日记」全状态个性化关怀文案方案》（产品最初的关怀系统设计文档）第 V–XI 节。
本文件把那份文档里"要不要接 AI、接在哪里"的讨论，落成一份可以拍板执行的具体计划。

---

## 1. 先说清楚：现在的规则引擎已经覆盖了什么

在讨论要不要加 AI 之前，先确认哪些事**已经不需要** AI：

- **情绪 × 关联因素的关怀文案**（`FACTOR_COPY`，10 种关联因素 × 3 档情绪）—— 纯规则匹配，已上线
- **Adaptive Care Flow**（点击低落/很糟后的即时归因 + 响应 + 小行动）—— 纯规则匹配，已上线
- **情绪植物图鉴的品种匹配**（`resolveSpecies`）—— 纯规则匹配，已上线
- **多因素合成句子**（`buildCombinedLead`）—— 目前是模板拼接（"今天好像很多事情撞在了一起——A、B方面的事凑在了一起…"），不是真正的语言理解，但已经能用
- **月度统计 / 情绪趋势 / 日历热力图 / 关联发现卡**—— 纯统计，已上线

这些都不需要 AI，也不应该为了"看起来更智能"而替换成 AI——规则引擎的好处是**确定性强、没有 API 成本、不用担心生成内容跑偏**，这些优点在这几个场景里都比"更自然的表达"重要。

## 2. AI 唯一值得介入的三个场景

沿用最初方案里的判断，AI 只做规则引擎做不到的事：

1. **自由文本理解**——用户在"我想说说""帮我理一理"里写下的话，目前只是原样存进 `note` 字段，产品从来没有"读懂"过它。
2. **多因素自然语言合成**——`buildCombinedLead` 现在是模板句，AI 可以把"低落 + 工作学业 + 睡眠 + 独处"这种组合，合成一句真正针对这个具体组合的话，而不是套模板。
3. **长期叙事总结**——现在"我的"和花园成熟时只有数字统计（"这个月照顾了自己 12 天"），没有"回顾这段时间"式的一段话总结。

这三件事的共同点：**都是"表达"层面的工作，不是"判断"层面的工作**。判断（该不该展示安全提示、该推荐呼吸还是推荐休息）永远由规则引擎做，AI 只负责把已经决定好的内容说得更自然，或者理解用户写了什么。这条边界很重要，见第 6 节。

## 3. 架构：为什么不能直接在前端调用 API

现状是纯静态站点（HTML/CSS/JS，托管在 GitHub Pages），没有后端。任何 API Key 一旦写进前端代码，几小时内就会被扒走滥用。

**结论：做这个功能的前提，是先有一个后端代理**，哪怕只是一个最薄的转发层：

- 形态：一个 Serverless 函数（Cloudflare Worker / Vercel Edge Function 这个量级即可，不需要一台常驻服务器）
- 职责：只做一件事——接收前端发来的结构化请求，注入服务端保管的 API Key，转发给 LLM 服务商，把结果原样返回
- 明确不做：不做用户账号、不做对话历史存储、不做除转发外的任何逻辑（安全边界判断依然全部在前端的规则引擎里完成，见第 6 节）
- 成本量级：按每次调用 300–600 tokens、选用低成本模型估算，单次调用成本在"可忽略"量级；真正需要关注的是**调用频率的上限**——需要给每个用户/每天设置调用次数上限，防止异常调用把成本推高

这一步是硬性前置条件，不是"以后再优化"的事——没有后端代理，后面的一切都无法安全地做。

## 4. 隐私：不能默默打破"数据不上传"这个承诺

产品现在的定位和差异化卖点之一就是"所有数据只留在本地浏览器，不上传到任何服务器"（首页、"我的"页都有这句话）。一旦要调用云端 AI，这个承诺必须被**显式地、可撤回地**修改，而不是被技术实现默默绕过。

设计原则：

- **默认关闭**。AI 关怀是一个需要用户主动打开的功能，不是新版本更新后自动生效的行为。
- 打开的入口放在"我的"页新增一个"AI 智能关怀"开关，打开时需要一个**独立的二次确认弹窗**，说清楚"打开后，你写的文字可能会被发送到第三方 AI 服务用于生成关怀文案"，不能用一句笼统的隐私政策带过。
- **分项授权，不是一键全开**：
  - 当前情绪档位 —— 默认允许发送
  - 关联因素标签 —— 默认允许发送
  - 自由书写的文字（note 字段）—— **默认不发送**，需要用户额外单独勾选。这是最敏感的一项，也是 AI 能发挥最大价值的一项，两者需要用户自己权衡，产品不替用户做这个选择。
- 关闭开关后，本地不应该再缓存任何已经发送过的历史内容用于"训练"或"个性化"——每次调用都是无状态的单次请求，不建立用户画像。

## 5. 分阶段实施

不建议一次性把三个场景都做了，按价值和风险从低到高排：

**Phase 1 —— 自由文本理解（最小可用版本）**
只做一件事：用户写下文字后，AI 生成一句共情式的回应（类似"听起来今天真的很不容易"这个量级），不生成建议、不做归因、不替代现有的规则推荐。这是风险最低、最容易验证效果的切入点。

**Phase 2 —— 多因素自然语言合成**
只在原有 `buildCombinedLead` 的触发条件下（低落/很糟 + 2 个以上关联因素）用 AI 替换模板句，其余场景不受影响。可以直接 A/B 对比模板版和 AI 版哪个用户反馈更好。

**Phase 3 —— 长期叙事总结**
在花园"种满一片"或月末，生成一段"回顾"式的总结。这个场景对生成内容的准确性要求最高（因为是对一整段时间的概括，出错的代价比单次回应更大），放在最后做。

每个 Phase 之间应该有真实用户反馈作为是否继续的判断依据，不是按固定排期往下推。

## 6. 安全边界：AI 不能替规则引擎做判断

这是整个计划里最重要的一条原则，必须写进系统提示词和代码逻辑里，而不是只停留在文档里：

- **AI 只负责表达，规则引擎负责判断**。是否触发安全提示（连续多日低落）、是否推荐呼吸练习、是否展示"陪我缓一下"——这些判断永远由现有的规则代码决定，AI 的输出不能覆盖或绕过这些判断。
- 用户输入中如果命中自伤/自杀相关的关键词，必须**在请求发到 AI 之前**就被本地规则拦截，直接展示现有的安全引导内容（现有 `safety-banner` 逻辑的延伸），不把这类内容发给 AI 处理，也不等 AI 的回复来决定要不要展示安全提示。
- 系统提示词里明确写死：不诊断、不给医疗建议、不假装是心理咨询师、语气必须和现有规则文案的调性一致（不评判、不说教）。
- 生成内容有长度上限和格式约束，防止出现结构混乱或跑题的输出。

## 7. 上线前的验证方式

- 开发阶段：人工检查至少 30–50 条真实场景（覆盖 5 档情绪 × 常见因素组合）生成的内容，确认没有一条出现说教、诊断化、或语气不符的表达。
- 上线初期：复用现有的 `care-feedback` 反馈模式（好一点/差不多/更糟），给 AI 生成的内容单独加一个"这句话有帮助吗"的轻量反馈，数据存本地，不上传。
- 观察至少两周真实使用反馈后，再决定是否推进到下一个 Phase。

## 8. 还没有答案、需要用户（产品负责人）拍板的问题

- 选择哪家 LLM 服务商、由谁承担 API 调用成本——这不是纯技术决定，涉及预算。
- 是否值得为了这一个功能，单独维护一个后端服务——多了一个需要长期运维的组件，即使很薄。
- "数据不上传"这个现有定位要不要因为这个功能被重新表述——如果做，产品的隐私承诺需要从"绝对不上传"改写成"默认不上传，你可以选择打开"，这是一次对外承诺的变更，不只是加一个开关那么简单。

在以上三点有明确答案之前，不建议开始写代码。

## 更新：BYOK 架构已上线，绕开了"必须先有后端"这个前提

产品负责人提出了一个更简单的路径：**不用我们自己的 API Key，让用户带自己的 Key 来用**
（Bring Your Own Key）。这直接绕开了第 3 节的架构前提——已经核实 Anthropic 官方支持
`anthropic-dangerous-direct-browser-access` 请求头，允许浏览器直接调用其 Messages API，
不需要任何后端中转（2024 年 8 月上线的官方能力，专门为这种"个人用自己的 Key"场景设计）。

**已经实现的 v0**（对应第 5 节 Phase 1 的极简子集）：

- 呈现方式改成了"小萤"——花园里的一只小萤火虫，而不是一个生硬的"AI 智能关怀"功能入口；
  "我的"页设置卡片、聊天界面标题、按钮文案都用这个角色名，但隐私说明里仍然清楚写着
  "小萤说的话由 AI 生成"，不是刻意隐瞒，只是换一种更贴合花园调性的呈现
- "我的"页新增设置卡片：默认关闭，用户选一家服务商、填入自己的 API Key 才能唤醒小萤
- **支持四家服务商**，逐个用 curl 发 CORS 预检请求实测过，只留下真的能从浏览器直连
  成功的：Anthropic（Claude）、DeepSeek、智谱 GLM、通义千问（阿里云百炼兼容模式）。
  DeepSeek/智谱/通义千问都是 OpenAI 兼容的 `chat/completions` 格式，共用一套请求逻辑；
  Anthropic 单独处理（`messages` API + 官方的浏览器直连头）。**没有加 OpenAI**——实测
  它的 API 会在 CDN 层直接拦掉浏览器来源的预检请求，加了也用不了，加一个用不了的选项
  比不加更糟
- Key 只存在这台设备的 `localStorage`，对话内容直接从浏览器发到用户选的那家服务商，
  我们自己完全看不到 Key 也看不到聊天内容——原文档"隐私"一节的分项授权设计暂时简化了：
  现在是"整个开关开/关"，还没做"自由文字单独授权"那一层，如果要更细，需要再补
- 默认服务商是 Anthropic，模型用 `claude-haiku-4-5-20251001`（低成本档位，成本由
  用户自己的 Key 承担）；其余三家分别用 `deepseek-chat`/`glm-4-flash`/`qwen-turbo`
- 一个独立的陪聊界面（`view-ai-chat`，标题显示为"小萤"），系统提示词把角色设定写死为
  "住在情绪花园里的小萤火虫"，同时保留：不诊断、不给医疗建议、不自称AI、每次最多
  2-3 句话、可以温和追问但每次最多一个问题——对应第 16 节的输出限制
- 聊天气泡里小萤的消息带一个小小的萤火虫头像（复用花园里本来就有的萤火虫素材，裁掉
  周围透明留白后单独存了一份 `assets/sprite-firefly-avatar.png` 给小尺寸场景用）
- 在低落/很糟的 Care Flow 里，如果用户已经开启小萤，会多一个"去找小萤说说"的入口

**没有做的**：多因素自然语言合成（Phase 2）、长期叙事总结（Phase 3）、Brain Dump 的 AI
整理、分项隐私授权。这些仍然可以按原计划的顺序推进。

**安全边界怎么接的**：发给 AI 之前，用户输入先过本地的 `checkSafetyRisk` 短语库（见
`docs/v2.1-care-experience-plan.md` 的 Safety Flow 部分）——命中的话直接不发给 AI，走
独立的安全引导界面。AI 自己的回复也会再过一次同样的检测，双重保险。系统提示词里也单独
写了一句：如果内容像是有自伤/自杀风险，AI 只回一句"这句话我想认真对待"就停止，不要自己
尝试安慰或处理——但这只是兜底，不是主要防线，主要防线是本地规则，不依赖 AI 判断对错。
